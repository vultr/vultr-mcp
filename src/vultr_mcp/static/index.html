Vultr MCP Server

Manage your Vultr cloud — instances, Kubernetes, DNS, databases, storage and more — from any MCP-compatible AI agent, in natural language. This page is for humans; AI clients connect to the same URL over the MCP protocol.

Endpoints

The base URL is https://vultrmcp.com/. The root exposes the full tool surface through one connection. Each category also gets its own endpoint exposing only that category's tools — useful when your client has limited connection slots or you want a smaller, cheaper tool set.

https://vultrmcp.com/                    # all tools (one connection)
https://vultrmcp.com/instances           # VPS instance tools only
https://vultrmcp.com/kubernetes          # VKE tools only
https://vultrmcp.com/dns                 # DNS tools only
https://vultrmcp.com/container-registry  # multi-word categories are slugified

Common categories: instances, baremetal, kubernetes, dns, firewall, block, snapshot, load-balancer, managed-databases, container-registry, vpcs, object-storage, billing, account. Paths are bare — no trailing slash needed.

Authorization

Two ways to authenticate. Both end up talking to api.vultr.com as you.

1. OAuth (zero-config)

Point your MCP client at https://vultrmcp.com/ and start the connection. You'll be redirected to Vultr to sign in and consent — no client ID or secret to paste, no API key to manage. Your client stores the resulting token and reuses it. This is the smoothest path for GUI clients with a browser handy (e.g. Claude).

2. API key (header)

Send your Vultr API key as a Bearer token on every request:

Authorization: Bearer YOUR_VULTR_API_KEY

Get a key from the Vultr console → Account → API. This is the most reliable path for headless/terminal agents and the only way to deterministically pick which organization you act on (see caveats).

Header name matters. Because the OAuth layer is active, a raw API key must arrive as Authorization: Bearer <key>. The alternate X-Vultr-API-Key header only works on a deployment with no OAuth layer.

Connecting with OAuth

These clients support the zero-config OAuth flow: point them at the root URL with OAuth enabled and finish sign-in in your browser. No client ID, secret, or API key to manage — the server registers itself and stores the token for you.

Claude.ai

  1. Settings → Connectors → Add custom connector.
  2. Paste https://vultrmcp.com/ and click Connect.
  3. A Vultr sign-in tab opens — sign in and approve.
  4. The connector flips to Connected; tools appear in chat.

opencode

Add the remote server with no header (OAuth is auto for remote servers):

{
  "mcp": {
    "vultr": {
      "type": "remote",
      "url": "https://vultrmcp.com/",
      "enabled": true
    }
  }
}

First use opens the browser to authorize.

Hermes Agent

In ~/.hermes/config.yaml, use auth: oauth instead of a header:

mcp_servers:
  vultr:
    url: "https://vultrmcp.com/"
    auth: oauth

Start Hermes (or /reload-mcp) and complete sign-in in the browser.

OpenClaw

Add with --auth oauth, then log in:

openclaw mcp add vultr \
  --url https://vultrmcp.com \
  --transport streamable-http \
  --auth oauth
openclaw mcp login vultr

login opens the browser flow and caches the token.

Claude Desktop (bridge)

Builds without native remote MCP use mcp-remote with no header — it runs the OAuth flow on first launch and caches the token under ~/.mcp-auth:

npx -y mcp-remote https://vultrmcp.com/

Any MCP client

If it advertises OAuth support for remote (Streamable HTTP) servers, give it https://vultrmcp.com/ and leave credentials blank. The server drives the rest of the flow shown above.

Which organization? The consent screen has no org picker — the token binds to whichever org your Vultr session is in at sign-in (usually your owner/primary org). If you need a specific org, use API-key mode instead. See Caveats.

Consuming it

Any client that speaks Streamable HTTP MCP can connect natively — give it the URL and (for API-key mode) an Authorization header. Clients that only support local stdio servers can bridge to the remote URL with mcp-remote:

npx -y mcp-remote https://vultrmcp.com/ --header "Authorization: Bearer YOUR_VULTR_API_KEY"

Swap the root URL for a category endpoint (e.g. https://vultrmcp.com/instances) to load a smaller tool set.

Setup per code harness

Config shown for API-key mode (most portable). For OAuth, drop the headers/token and use each tool's OAuth switch, noted per harness.

opencode

Add to opencode.json (project root) or ~/.config/opencode/opencode.json:

{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "vultr": {
      "type": "remote",
      "url": "https://vultrmcp.com/",
      "enabled": true,
      "headers": { "Authorization": "Bearer YOUR_VULTR_API_KEY" }
    }
  }
}

opencode auto-attempts OAuth for remote servers. To force API-key mode and skip OAuth, add "oauth": false alongside the header.

Hermes Agent

Add under mcp_servers in ~/.hermes/config.yaml, then /reload-mcp (or restart):

mcp_servers:
  vultr:
    url: "https://vultrmcp.com/"
    headers:
      Authorization: "Bearer YOUR_VULTR_API_KEY"

For OAuth instead of a header, replace the headers block with auth: oauth.

OpenClaw

Add via the CLI (writes to ~/.openclaw/openclaw.json under mcp.servers):

# API-key mode — set the header in openclaw.json after adding, or:
openclaw mcp add vultr --url https://vultrmcp.com --transport streamable-http

# OAuth mode
openclaw mcp add vultr --url https://vultrmcp.com --transport streamable-http --auth oauth
openclaw mcp login vultr

Use --transport streamable-http (not SSE). For a static key, add a headers object to the server entry in openclaw.json rather than committing it to the CLI history.

Claude Desktop / Claude.ai

Claude.ai: add a custom connector with the URL and complete the OAuth flow. Claude Desktop builds that don't support remote URLs natively use the mcp-remote bridge shown above under a vultr entry in claude_desktop_config.json.

Caveats & gotchas

Multiple organizations

Every Vultr credential is scoped to exactly one organization — the API resolves the org from the credential itself, and there is no per-request org switch. To use two orgs, add two connections, each with that org's own API key. This is the only way to target a specific org deterministically.

OAuth binds to your active org — with no picker. The consent flow has no organization selector; the token silently binds to whichever org your Vultr console session is in when you click Authorize (in practice, your owner/primary org). If you need a specific org, use API-key mode. Double-check the intended org before consenting.

OAuth support varies by client

Zero-config OAuth relies on the client supporting the MCP OAuth flow (authorization code + PKCE + dynamic client registration). GUI clients with a browser handle this best. On a headless server or a harness with immature OAuth support, prefer API-key mode — it always works.

Corporate VPN / TLS interception

If your network does TLS interception, node-based bridges (mcp-remote) may reject the certificate. Point Node at your VPN's CA with NODE_EXTRA_CA_CERTS=/path/to/ca.pem rather than disabling TLS verification.

Identity tools are excluded

API-key, user, IAM, SCIM, organization and OIDC management tools are intentionally not exposed, so an agent can't rotate credentials or alter identity. Manage those in the Vultr console.
