Vultr MCP Server

Inspect your Vultr cloud — instances, Kubernetes, DNS, databases, storage and more — from any MCP-compatible AI agent, in natural language. This page is for humans; AI clients connect to the same URL over the MCP protocol.

Read-only. Every tool on this server reads — listing, describing, and reporting on your Vultr resources. Nothing creates, changes, or deletes infrastructure, so an agent connected here cannot spend money or break a running service. Write access is coming as an opt-in you enable per user in the Vultr console.

Endpoints

The base URL is https://vultrmcp.com/. The root exposes the full read-only tool surface through one connection. Each category also gets its own endpoint exposing only that category's tools — useful when your client has limited connection slots or you want a smaller, cheaper tool set.

The root doubles as this page: only a top-level browser navigation gets the docs, so MCP clients — including browser-based agent UIs — reach the protocol at the same URL. Both https://vultrmcp.com and https://vultrmcp.com/ work; the trailing-slash form is canonical.

https://vultrmcp.com/                    # all tools (one connection)
https://vultrmcp.com/instances           # VPS instance tools only
https://vultrmcp.com/kubernetes          # VKE tools only
https://vultrmcp.com/dns                 # DNS tools only
https://vultrmcp.com/container-registry  # multi-word categories are slugified

The root serves all of these combined; each endpoint below serves only its own tools. Click one to see the tools it exposes. Append the path to the base URL — e.g. https://vultrmcp.com/load-balancer.

Authorization

Two ways to authenticate. Both end up talking to api.vultr.com as you.

1. OAuth (zero-config)

Point your MCP client at https://vultrmcp.com/ and start the connection. You'll be redirected to Vultr to sign in and consent — no client ID or secret to paste, no API key to manage. Your client stores the resulting token and reuses it. This is the smoothest path for GUI clients with a browser handy (e.g. Claude).

2. API key (header)

Send your Vultr API key as a Bearer token on every request:

Authorization: Bearer YOUR_VULTR_API_KEY

Get a key from the Vultr console → Account → API. This is the most reliable path for headless/terminal agents and the only way to deterministically pick which organization you act on (see caveats).

Header name matters. Because the OAuth layer is active, a raw API key must arrive as Authorization: Bearer <key>. The alternate X-Vultr-API-Key header only works on a deployment with no OAuth layer.

Connect your client

Point any MCP client at the root URL — or a category endpoint for a smaller tool set — and authenticate one of two ways: zero-config OAuth (sign in through the browser, nothing to paste) or an API-key Bearer header. Both are shown per client below. The OAuth handshake looks like this:

Which organization? The OAuth consent screen has no org picker — the token binds to whichever org your Vultr session is in at sign-in (usually your owner/primary org). To target a specific org, use API-key mode. See Caveats.

Steps reflect current UIs (mid-2026); vendor labels shift, so treat them as a guide.

Claude.ai

  1. Settings → Connectors → Add custom connector.
  2. Paste https://vultrmcp.com/ and click Connect.
  3. A Vultr sign-in tab opens — sign in and approve.
  4. The connector flips to Connected; tools appear in chat.

Cursor

  1. Settings → Cursor Settings → Tools & MCP.
  2. Add custom MCP → in mcp.json set "type": "http", "url": "https://vultrmcp.com/".
  3. Save → Needs login opens the browser OAuth flow (or add an Authorization: Bearer header for API-key mode).
  4. Tools appear under Available Tools.

VS Code

  1. Open the MCP Servers panel (agent customizations view) — or edit mcp.json (repo root or .vscode/mcp.json).
  2. Click + to add a server (or Browse Marketplace) → custom HTTP server, URL https://vultrmcp.com/.
  3. On the auth challenge, sign in through the browser (or add an Authorization: Bearer header for API-key mode).
  4. It appears under Workspace / User with a green check; tools are live in agent chat.

Codex CLI

  1. codex mcp add vultr --url https://vultrmcp.com/
  2. OAuth: codex mcp login vultr opens the browser.

API-key / headless — in ~/.codex/config.toml:

[mcp_servers.vultr]
url = "https://vultrmcp.com/"
bearer_token_env_var = "VULTR_API_KEY"

opencode

In opencode.json — omit headers for auto-OAuth, or add one for API-key mode:

{
  "mcp": {
    "vultr": {
      "type": "remote",
      "url": "https://vultrmcp.com/",
      "enabled": true
    }
  }
}

Hermes Agent

In ~/.hermes/config.yaml — auth: oauth, or a headers block for API-key mode:

mcp_servers:
  vultr:
    url: "https://vultrmcp.com/"
    auth: oauth

OpenClaw

openclaw mcp add vultr \
  --url https://vultrmcp.com \
  --transport streamable-http \
  --auth oauth
openclaw mcp login vultr

login opens the browser flow and caches the token.

Claude Desktop & stdio-only clients

Clients without native remote MCP (older Claude Desktop, Zed, others) bridge via mcp-remote — OAuth runs on first launch; add --header for API-key mode:

npx -y mcp-remote https://vultrmcp.com/

Any MCP client

Native remote (Streamable HTTP): give it https://vultrmcp.com/ and either leave credentials blank for OAuth or set Authorization: Bearer YOUR_VULTR_API_KEY. stdio-only: use the mcp-remote bridge above.

Caveats & gotchas

Multiple organizations

Every Vultr credential is scoped to exactly one organization — the API resolves the org from the credential itself, and there is no per-request org switch. To use two orgs, add two connections, each with that org's own API key. This is the only way to target a specific org deterministically.

OAuth binds to your active org — with no picker. The consent flow has no organization selector; the token silently binds to whichever org your Vultr console session is in when you click Authorize (in practice, your owner/primary org). If you need a specific org, use API-key mode. Double-check the intended org before consenting.

OAuth support varies by client

Zero-config OAuth relies on the client supporting the MCP OAuth flow (authorization code + PKCE + dynamic client registration). GUI clients with a browser handle this best. On a headless server or a harness with immature OAuth support, prefer API-key mode — it always works.

Corporate VPN / TLS interception

If your network does TLS interception, node-based bridges (mcp-remote) may reject the certificate. Point Node at your VPN's CA with NODE_EXTRA_CA_CERTS=/path/to/ca.pem rather than disabling TLS verification.

Identity tools are excluded

API-key, user, IAM, SCIM, organization and OIDC management tools are intentionally not exposed, so an agent can't rotate credentials or alter identity. Manage those in the Vultr console.

No write tools yet

The server currently exposes reads only, so an agent can report on your infrastructure but not change it — ask it to create, resize, or delete something and it will tell you it has no tool for that. Provisioning stays in the Vultr console or the API for now. Write tools will arrive as an opt-in you turn on per user within your organization, so the safe surface stays the default for everyone who doesn't.
